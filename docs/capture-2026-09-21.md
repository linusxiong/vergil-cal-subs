**English** | [简体中文](capture-2026-09-21.zh-CN.md)

Recorded on September 21, 2026. The user completed the university login from the beginning in a separate browser and explicitly requested that the session be recorded and archived. The request capture window was 18:56:11–19:00:22 UTC (14:56:11–15:00:22 in New York). It captured 172 requests, 168 responses, and one token-exchange summary.

This document and the [machine-readable summary](capture-summary.json) contain evidence suitable for publication, not a complete HAR. The original recording retained only metadata with sensitive fields redacted and field structures bounded by depth and count; it did not retain complete tokens, passwords, verification codes, or cookies. This repository also excludes raw logs, browser profiles, personal courses, and the exported personal ICS to keep temporary session URLs and identity information out of the public source history. `output/`, HAR files, environment files, and local databases are ignored.

## Mapping evidence from the public frontend

Public build inspected: [Vergil main.a3f63669067473db.js](https://vergil.columbia.edu/main.a3f63669067473db.js). This filename may change when the university publishes a new build.

| Information | Structure used by the public frontend |
| --- | --- |
| Student UNI | The portion of UserInfo `sub` before `@` |
| Token storage | OAuthStorage uses `localStorage` and reads the `access_token` / `refresh_token` keys |
| Courses / classes | `data.courses[].class_data.classes[]` |
| Meeting arrangements | `meeting_details[]` |
| Date range | `begin_date`, `end_date` |
| Weekly pattern | `meeting_pattern.meetingpatterndetail_set[]` |
| Weekday and time | `week_day`, `from_time`, `to_time` |
| Location | `room.room_code`, `room.building.building_name`; `room.room_name` for special rooms |

The adapter accepts both Columbia email-shaped subjects and bare UNIs. It verifies the Access Token with the university's UserInfo endpoint instead of trusting a client-supplied student ID or a locally decoded JWT without signature verification. Invalid data formats are rejected without overwriting the saved schedule.

The personal ICS supplied for inspection expanded classes into UTC events by date, which can accommodate New York daylight saving time changes. That file did not provide usable location information and does not establish the availability of complete address fields. Open-source tests construct synthetic courses and do not copy the student's course titles, schedule, or event UIDs.

| Meeting-data mapping | Based on public university frontend code and synthetic tests; complete live responses were not retained |
| Long-term background sync and automatic retention of Refresh Tokens | Not implemented in this version; each sync requires an Access Token, with an optional Refresh Token |
| School-specific closure rules, street addresses, and university API quotas | Not confirmed; manual date exclusions and known building / room information are supported |

An ordinary third-party website cannot read tokens from university pages simply by opening the university login page. A mobile app's system-browser login also does not automatically obtain another client's credentials. Observing these requests depended on locally authorized CDP diagnostics; it was not a product login interface available to websites.

The current workflow requires users to explicitly provide their own tokens to a trusted deployment. The service requests only their own schedule and stores snapshots. This is not a formally registered, read-only OAuth authorization flow. The university client's broad token permissions, permission for third-party access, and hosting requirements remain external constraints for deployers to confirm.

## Later production validation on the same day

Authorized production requests exposed two compatibility issues: Cloudflare's runtime rejected `redirect: "error"` with a TypeError before sending the request, and the university's JSON:API endpoints returned 406 when the request accepted only `application/json`. The implementation now uses `redirect: "manual"`, rejects all unsuccessful responses, and does not follow redirects. Person and course APIs use `Accept: application/vnd.api+json, application/json`; OAuth endpoints continue to use `application/json`. Error responses contain only fixed endpoint paths, HTTP statuses, or safe error categories, with no upstream payloads, query parameters, identities, or credentials.

After those fixes, the production Cloudflare API returned 201 for creation, 200 for ICS and management retrieval, 204 for revocation of the temporary validation subscription, and 404 for its ICS after revocation. Credentials and real course contents were not written to the repository or diagnostic files. This validation used a valid Access Token and did not trigger refresh, so it does not confirm the Refresh Token grant.
